Ascend 910B3vsH20

LLaDA2.1-mini(diffusion LLM,MoE,256 专家 top-8)在大 batch 吞吐场景下的对比分析:roofline、单卡实测、专家并行(EP)评估与后续方向。

—

结论

1

大 batch + 短到中等序列下 910B 略优于 H20。 512in/2048out 输出吞吐 2591 vs 2364(+10%),短序列 gsm8k +7%。但更长输入(4K in/1.5K out)H20 反超 ~1.4×(910B 受 64GB 显存限制只能到 bs≈72,低 bs 下 MoE 更带宽受限;完整机理待 profiling)。

2

小 batch 下 910B 明显落后。 bs=1 时 910B 约为 H20 的 0.5×(312 vs 592),bs=8 约 0.4×。

3

专家并行(EP)通信代价过大,当前不划算。 128 blocks/卡 实测 a2a 12.2 ms/层,节点吞吐只有 4 张独立单卡的 1/4.6。

算力比(2.16×)与带宽比(2.5×)接近互为倒数。因此算力受限的算子 910B 快约 2.16×,带宽受限的算子 H20 快约 2.5×,计算与带宽各占一半的 workload 两者相当。胜负取决于给定 bs 下各算子落在 ridge 的哪一侧。

1.2 各算子的算术强度(AI)与瓶颈

AI = 计算量(FLOP) / 访存量(byte),决定算子落在 ridge 哪一侧(AI > ridge 算力受限,AI < ridge 带宽受限;ridge = 算力峰值/带宽,910B 320T/1.6=200,H20 148/4.0=37)。算法:GEMM(有权重复用) AI = 2·M·K·N / (K·N·2B) = M(参与该权重的行数)——MoE 的 M = 每专家 token 数 t,dense 的 M = bs×block;attention AI = KV 复用 = block × GQA组 = 32×4 = 128;vector 每元素读写各一次 → AI ≈ 1。例(bs=128):MoE t = 128×32×8/256 = 128,dense M = 4096。

attention (FIA)= 128128<200 边缘128>37 算力~平

只有 MoE 的 AI 随 bs 变化(AI = t = 每专家 token 数 ∝ bs),所以打大 batch 只对 MoE 有意义。vector(AI≈1)与 attention(AI≈128,由 dLLM block 32 × GQA 组 4 的 KV 复用决定)的 AI 都与 bs 无关。attention 在 H20 上算力受限、910B 上带宽受限,两者相当。

贴回 ridge(910B 200 / H20 37):dense 进算力区(AI>200)AR 需 bs≥200、dLLM 只需 bs≥7;MoE 甜点(t≥512)AR 需 bs≥16384、dLLM 只需 bs≥512;attention 从 AR 的 AI=4(带宽受限、favors H20)抬到 dLLM 的 128。AR 小 bs 全是带宽受限(favors H20);dLLM 靠 block 把算子推向算力受限(favors 910B)——这是 dLLM 本身就更适合算力强芯片的根因。

1.4 小结

小 bs(≤128)MoE 在 910B 带宽受限(仅用 39% 算力),2× 算力优势用不出;vector 带宽受限 H20 有利,attention 相当。910B 靠 dense GEMM 的算力优势扳平,整体约 1.06× 的小幅领先或相当。
大 bs把 t 推到 ≥512 时 910B 的 MoE 才进算力区、2× 优势才兑现。单卡 bs=128 只有 t=128,堆 t 需 DP+EP(第三章)。大 bs 是 910B 的杠杆、不是 H20 的(H20 的 MoE 在 t=29 即饱和)。

03

专家并行(EP)评估

3.1 为什么评估 EP

超过 H20 需把 MoE 推进算力区(t≥512),但单卡 bs=128 只有 t=128。EP 让每个专家收所有 DP 副本的 token:DP8+EP8、每卡 bs=128 → 每专家 t=1024,理论上进入甜点。附带把每卡权重从 30.6GB 降到 3.8GB,腾出约 55GB 给 KV。

实测结果(910B):DP8+EP8 跑通,gsm8k 0.835(与单卡持平);MoE 进入甜点(GroupedMatmul 273-282 TFLOPS = 85-88% 峰值,t/expert=729);显存释放兑现。架构假设成立。

3.2 通信代价的计算

一个 token 路由到 K=8 个专家,在 EP=P 下落在 r(P) = P·(1−(1−1/P)^K) 个 rank 上(deep_ep 按目标 rank 发一份)。出卡字节 = r(P)·H·2B·(P−1)/P,combine 返回 ×2;可用带宽 = P−1 条 HCCS 链路 × 15.6 GB/s。

ep目标 rank链路数可用带宽字节/token/层T=4096 时
21.99116 GB/s8.0 KB2.14 ms
43.60347 GB/s21.6 KB1.94 ms
85.257109 GB/s36.8 KB1.41 ms

ep 越大,每 token 搬的字节越多(8→37 KB),但链路数涨得更快(1→7),所以每 token 反而更便宜。单节点 8 卡,无 ep=16。（带宽按每链路 15.6 GB/s 线性取值。）

3.5 实测 a2a 与 roofline 的差距

实际跑的 DP4+EP4,实测 a2a = 12.2 ms/层,理论地板(① 互联地板)只有 2.84 ms/层——实测是地板的 4.3 倍,多出的 9.4ms 是可优化的库开销 + skew,不是物理下限。整轮 95ms(单卡)→ 488ms,节点吞吐只有 4 张独立单卡的 1/4.6。

3.6 结论

  • 大 batch(≥87 blocks/卡):roofline 上已净亏,当前实现的 a2a 又是地板的 ~4 倍。不建议使用。
  • 小 batch(≲87 blocks/卡):roofline 上有收益,但当前实现的 a2a 会把收益吃光。需先压库开销和 skew。
  • 下一代硬件:910C 互联翻倍把交叉点从 87 推到 130,刚好把 128 挪到有收益一侧,但余量很薄;收益天花板由模型结构决定,与互联速度无关。
  • 追吞吐用大 batch + 独立单卡,不用 DP8+EP8;EP 目前唯一成立的价值是显存(长序列档单卡放不下时用吞吐换容量)。
04

后续优化方向

dense 已算力饱和(78% 峰值、快于 H20 2×),不需改动。发力点两类:算法/结构协同(把 workload 往 910B 算力强项推)+ kernel 工程(FIA、融合核)。

4.1 算法方向:把 workload 往算力密集推

910B 在算力上占优、在带宽和小算子上吃亏。算法层面最有效的方向是把 dLLM 的结构往“更计算密集、更少带宽/小算子”改。

  • ① 把 block 做大。 block_size 决定 attention 和 MoE 的算术强度:attention AI = block × GQA组(4),block=128 → AI=512 >> ridge 200,进入算力区;MoE 的 t = block × bs × topk / experts,block=128、bs=128 → t=512,单卡即进入 MoE 甜点(EP 靠通信堆的 t,大 block 不用 a2a 就拿到)。参考:diffusion 版 Gemma 已做到 block_size=128。代价:block 内 token 更多,精度/收敛需验证。
  • ② Blockwise MoE:压缩 block 内激活的专家数。 一个 block 内的 token 语义相近,大概率路由到重叠的专家。把 block 的专家集合压到更少的 distinct 专家,可少读专家权重,直接降低 MoE 的权重带宽(30GB/forward 瓶颈)。参考:已有开源 dmoe。
  • ③ 全词表冗余裁剪。 每去噪步对全 32 位置算 lm_head(10.3ms)+ 全词表归约(6ms),但后期步骤 still-masked 位置很少、大部分冗余。只对 still-masked 位置算可大幅减少。障碍:JointThreshold 的 T2T 语义读所有非 mask 位置的概率,需重新设计算法。收益上界大,工程量也大。

4.2 attention FIA 效率(长序列)

910B FIA 只跑 24% MFU,seq4096 时 attention 占整步 33%(短序列 7%,不重要)。24% 是实现低效而非带宽限制:attention AI=128 < ridge 200 属带宽受限,MFU 上限本就是 ~40-64%,但 FIA 连这个都没达到(load pipe 和算力 pipe 都不饱和)。根因是 online-softmax 把 QK→softmax→AV 串成依赖链、cube/vector 交替互等产生气泡,而 NPU 不能靠多流重叠。靠核内融合可回收到 ~40-50%。

4.3 更少更胖的融合核

减 kernel 数 + 减冗余内存遍历。剩余目标:MoE 路由三段式融合(~3.5%)、norm/rope 进一步合并。单项收益不大(个位数 %),但可累积。

4.4 硬件代际

910C 互联翻倍(218 GB/s)时,EP 在 128blk/卡接近打平,大 batch + EP 进入甜点才真正可行。当前 910B3 上 EP 净亏,需下一代硬件。

∑

总结

维度结论
小 bs(≤128)相当 / 小幅领先 1.06×。910B 靠 dense 算力扳平 vector/routing 的带宽劣势,MoE 未进甜点。
大 bs(单卡)bs 天花板约 160,但无吞吐收益(MoE 仍带宽受限 + graph/KV 吃显存)。推荐 bs=128。
