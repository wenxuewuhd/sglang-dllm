GLM-5.3-Flash 昇腾适配评估

GLM-5.2 走的是 DeepSeek-V3.2 架构，昇腾侧已量产。GLM-5.3-Flash 是换了骨架的新模型：45 层 3:1 混合注意力（KDA 线性 + NoPE 稀疏 MLA）、mHC 取代残差、原生多模态、FP8 blockwise 权重。「在 5.2 基础上改一改」不成立。GPU 侧完整实现已公开在分支 xinyuan/glm-5.3-flash-support（144 文件 / +16.6k 行）；昇腾侧的对照物也比想象中全——kpool 与 mHC 都能照着 DeepSeek-V4 的昇腾支持做。真正要自研的收敛到三块。

§0结论速览

参考实现已经公开：分支 xinyuan/glm-5.3-flash-support

不在 main、不在任何 tag（main @ a3ae667d 里 glm5next 零命中），但代码已推送到公开 feature 分支 fa8735a4（2026-08-26），相对 main 144 文件 / +16,659 行。GPU 侧即由该分支 + 专用镜像 lmsysorg/sglang:glm-5.3-flash 提供支持。

因此昇腾适配有完整的 GPU 参考实现可对齐，模型定义那一项回落到 8–14 人日。代价换成了另一类风险：分支尚未 merge，接口仍会动，需要持续 rebase；且分支内 GLM-5.3 相关的新代码几乎不含 NPU 分支（glm5_next.py / communicator_mhc.py / dsa_backend.py / kpool 全家对 npu|ascend 命中数为 0），后端层要从头写。

三块要自研，两块有 DeepSeek-V4 的昇腾实现可照抄

先把最容易搞错的两条摆正：kpool 就是 DSA 的一部分，mHC 昇腾也已经有算子，两者的参照对象都不是 DeepSeek-V3.2，而是 DeepSeek-V4。

  • 有参照 kpool 稀疏索引 — 完全在 DSA indexer 内部：池化 index-K（pool_size=4）→ 在池化 key 上算 MQA logits（矩阵小 4×）→ 选 2048/4 = 512 个 pool → 展开回 2048 个 token → 追加未池化的尾部。topk 之后的稀疏 MLA 完全不变。昇腾 ascend_dsv4_backend.py 已有 torch.ops.npu.compressor + compress_ratio == 4 + is_in_indexer 的完整通路。15–25 人日。
  • 有参照 mHC — deepseek_v4.py 里 pre 和 post 都已有 NPU 分支（npu_hc_pre / torch.ops.custom.npu_hc_post），注释直接写 “mirroring the dsv4-flash source”。GLM-5.3 的真增量是通信编排（分支新增 communicator_mhc.py 565 + _hybrid_cp 222，要跟 KDA/DSA 混合 CP 配合），DSv4 那边没有。10–18 人日。
  • 自研 量化通路 — 最大单项。A2/A3 无原生 FP8 matmul，官方 checkpoint 不可直读；必须 BF16 → msModelSlim W8A8，且 34 个 KDA 层整层、mHC、indexer、ViT 全部进 ignore list，288 专家的校准要多轮。30–45 人日，详见 §3。
  • 自研 NoPE 稀疏 MLA 后端 — 模型层已由共享的 skip_rope 路径覆盖，剩下 Ascend MLA/DSA backend 与 mla_preprocess 要接受 rope_dim=0、KV latent 512、head_dim 256。20–32 人日。
  • 自研 分组 topk 算子 — kpool 里唯一真正没有对等物的一环：GPU 走 CUDA JIT fast_kpool_topk_transform_fused（group_topk ∈ 128/160/192/224/256/512）或 sgl_kernel.fast_topk_v2（2048）；代码对非 CUDA / 非 fp32 logits 是 raise NotImplementedError，昇腾要先解掉这个硬拦，再决定写算子还是先用 torch.topk 退化。已计入 kpool 的 15–25。

反过来，四件降工作量的好事

  • KDA 全套已在昇腾落地（AscendKDAAttnBackend + kda_gate/kda_prefill/kda_chunk_delta_h + causal_conv1d），且分支里 kda_backend.py 只改了 +108 行——印证 KDA 是「接线」而非「自研」。
  • DSA（lightning indexer + sparse_attn_sharedkv + compressor）已在 GLM-5.2 / DSv3.2 上量产。
  • VLM 复用度极高：Glm5NextVision* 直接继承 GlmOcrVision*，processor 走扩写后的 processors/glm4v.py（+489 行）——GLM-OCR 与 GLM-4.5V 在昇腾支持矩阵里都已 ✅。
  • 显存反而更轻松：只有 11 层全注意力，KV 是 GLM-5.2 的 1/6；W8A8 约 321 GB，A3 单节点 TP16 余量充足，A2 单节点 TP8 也放得下（GLM-5.2 的 W8A8 是 774 GB）。

按你的口径，MTP 暂不计入

投机解码（NextN）相关的 index_share_for_mtp_iteration、KDA target_verify、eagle NPUGraph 一并推到 P2（15–25 人日）。代价是 decode TPS 大约损失 1.5–2×，长期仍需补。好消息是昇腾侧 kda_target_verify.py 和 DSv3 MTP 路径都已存在，届时是接线而非从零。

NoPE 的工作量落在后端，不在模型层

分支里的做法比预期干净：全注意力层直接复用 DeepseekV2AttentionMLA(skip_rope=True)，qk_rope_head_dim=0 由共享路径里的两处早退处理——if not skip_rope and qk_rope_head_dim > 0 跳过 rotary_emb 构造，_concat_and_cast_mha_k 在 qk_rope_head_dim == 0 时直接返回 k_nope。forward_mha.py 里本来就有 _is_npu 分支，这部分改动昇腾是白拿的。

所以真正要做的是后端与 kernel 层：

  • Ascend MLA / DSA backend 接受 rope_dim=0，KV latent 从 576 变 512（去掉 rope 段）；
  • mla_preprocess 融合算子（RMSNorm→Dequant→MatMul→RoPE→ReshapeAndCache）需要一条无 RoPE 分支；
  • qk_head_dim=256 / v_head_dim=256 超出现有 tiling 假设（DSv3 是 192/128），UB 占用与分块要重算；
  • topk 索引 → cache 偏移的换算随布局改变。

补偿仍在：NoPE 意味着 KV cache 不含位置信息，prefix cache / RadixCache 的语义更干净，同一前缀在任意位置产生同样的 cache。

kpool = DSA 的一环，参照 DeepSeek-V4 而不是 V3.2

代码上就是二选一：indexer_cls = IndexerKPool if get_dsa_index_kpool(config) > 1 else Indexer，共享同一个 DeepseekV2AttentionMLA。流程是

  • 把 history 的 index-K 按 pool_size=4 池化 / 压缩写入 index cache；
  • 在池化后的 key 上算 MQA logits —— [M,N] logits 矩阵直接小 4 倍，正好砍掉 vLLM 点名的那个 DSA 瓶颈（logits 要先落地再逐行 topk）；
  • topk_from_pooled_history_logits 选 2048/4 = 512 个 pool；
  • expand_pooled_groups_to_topk 展开回 512×4 = 2048 个 token；
  • append_kpool_tail_to_topk 把未池化的尾部 token 追加（index_kpool_always_select_tail）。

topk 之后完全不变：输出仍是 [rows, 2048] 的 int32 索引（-1 padding），下游稀疏 MLA 一模一样 —— 昇腾的 sparse_attn_sharedkv 那半边直接复用。

昇腾侧的对照物是 DeepSeek-V4：hardware_backend/npu/attention/ascend_dsv4_backend.py 已经有 torch.ops.npu.compressor、compress_ratio == 4 的专门分支、per-ratio metadata、compressor.is_in_indexer（indexer 侧压缩）、state pool、Hadamard、fused cache。compressor 在 sgl-kernel-npu 的 CMake 里不在 A3_ONLY 门控内，ops-transformer 的 910b 与 a3 构建集里也都带它 —— A5-only 的是融合版 indexer_compress_epilog，不是基础 compressor。

因此真正要新做的收敛到三处：①分组 topk 算子（GPU 走 CUDA JIT fast_kpool_topk_transform_fused 或 sgl_kernel.fast_topk_v2；代码对非 CUDA / 非 fp32 logits 直接 raise NotImplementedError，要先解掉硬拦）；②打分（deep_gemm fp8_paged_mqa_logits → 昇腾 quant_lightning_indexer + flash_block_score_*，已有，需接池化 K 布局）；③压缩写 cache（kpool_softmax_rotate_write_cache → torch.ops.npu.compressor，语义要对齐：DSv4 是 compress-then-attend，GLM-5.3 是 pool-score-then-expand）。其余可移植：kpool_plan.py(871) 是纯 Python 调度，kpool_fp8_index.py(1720) 是 Triton + 普通 PyTorch（expand_pooled_groups_to_topk 就是 arange/gather/where）。

mHC 同理：DeepSeek-V4 在昇腾已有 pre 和 post

deepseek_v4.py 里两端都有 NPU 分支——if _is_npu: return _get_mhc_ops().npu_hc_pre(...) 与 if _is_npu: return torch.ops.custom.npu_hc_post(x, residual, post, comb)。npu_hc_pre 的 docstring 直接写 “mirroring the dsv4-flash source”，sinkhorn 在 fp32 迭代；唯一要注意的是它不折叠 input_layernorm（返回 norm_fused=False，caller 自己补 RMSNorm）。

A2/A3 上可用，这一点是闭合的，三条互相印证：① 昇腾支持矩阵里 Eco-Tech/DeepSeek-V4-Pro-w4a8-mtp 与 Eco-Tech/DeepSeek-V4-Flash-w8a8-mtp 都是 A2 ✅ / A3 ✅，还配了专门量化好的权重 —— 而 DSv4 没有 mHC 根本跑不起来；② 上面两个 if _is_npu: 分支没有非-NPU fallback，算子缺失只会硬报错，不会静默降级；③ 全仓 grep ascend950 / soc_version / npu_arch，SGLang 的 NPU 后端没有任何运行时代际门控——这与 RFC #35709 的设计原则一致（build-time 分派，wheel 编译时选定 provider）。

一个容易读错的地方：hc_post 只出现在 sgl-kernel-npu 的 --soc=ascend950 构建集里，但这不等于 A2/A3 缺失。那份列表是 ops-transformer 这一个 provider 的 A5 专属实现（同列表里还有 kv_quant_sparse_attn_sharedkv、indexer_compress_epilog、moe_gating_top_k 等 A5 重写版），而 torch.ops.custom.* 走的是另一个 provider cann-recipes-infer/ops/ascendc，其 CI 对 a3 / 910b / 950 三档都执行了 build.sh -c <soc>。两个列表里 compressor 同时出现，就说明它们是按 provider 划分而非能力分层。

GLM-5.3 的真增量是通信编排：分支新增 communicator_mhc.py(565) 与 communicator_mhc_hybrid_cp.py(222)，要跟 KDA/DSA 的混合 CP 协同，DSv4 那边没有对应物。这部分昇腾侧要自己对齐。

§3量化：FP8 → 什么

这是与 GLM-5.2 差异最大、也最容易低估的一块。5.2 有现成的社区 w8a8 权重可下，5.3 没有；而且官方 checkpoint 的 FP8 blockwise 格式在 A2/A3 上根本没有执行路径。

FP8 → MXFP4：有损，且在 A2/A3 上这个选项不存在

先说结论：如果目标硬件是 A2/A3，问题不成立——MXFP4 相关的三个 scheme 在昇腾上是 A5/950 专属，底层算子 A2/A3 没有。只有上 A5 才谈得上。

真上了 A5，答案是有损，而且损失明显大于 8bit 档：

  • MXFP4 = 4bit E2M1 + 每 32 个元素一个 E8M0（只能取 2 的幂） 的 scale。相对 FP8 e4m3 + 128×128 block scale，比特数减半、scale 无小数精度。NVIDIA 自己的口径是 MXFP4 相对 FP8 有 “noticeable accuracy drop” 风险；同为 4bit 但 scale 更细（16 元素 + E4M3 scale）的 NVFP4 在 DeepSeek-R1 上才做到 ≤1%，MXFP4 的粗 scale 只会更差。
  • 不要做级联量化。 FP8 checkpoint 本身已经损失过一次，在它上面再压到 4bit 会叠加误差。正确起点是官方另发的 zai-org/GLM-5.3-Flash-BF16（同样 321B），或用 fp8_cast_bf16 类脚本反量化，然后一次性量化到目标格式，并配 AWQ / GPTQ / AutoRound / Hadamard 做误差补偿。msModelSlim 本身也只接受 BF16 输入。
  • GLM-5.3 有三类模块对低比特特别敏感，4bit 档必须全部排除：mHC（Sinkhorn 后噪声会迅速放大，llama.cpp 移植 DSv4 的实测结论是 hc_* 必须留高精度）、KDA 的 gate / A_log / dt_bias / short-conv（fp32 state 递推）、indexer 与 ViT。
  • 顺带一个反直觉但有据的结论：8bit 档 INT 优于 FP（MXINT8 在 12 个模型上全面胜过 MXFP8，含 Qwen3-30B-A3B / 235B-A22B 这类 MoE）；4bit 档反过来 FP 优于 INT，除非加 Hadamard 旋转后 INT4 才反超。也就是说昇腾走 INT8 路线在精度上不吃亏，甚至更好；要压到 4bit 才需要认真做离群抑制。

官方 FP8 checkpoint 里，KDA 层整层就是 BF16

容易只排掉 gate 就以为够了。quantization_config.modules_to_not_convert 把 KDA 的每一个权重都列了进去：

SGLang 分支的实现比 checkpoint 更严：A_log 与 dt_bias 直接声明成 torch.float32，qkv_conv1d 用 params_dtype=torch.float32，kda_backend.py 还断言 conv_weights.dtype == float32 且 ssm_states.dtype == float32。所以 KDA 状态池不能降到 bf16 省显存 —— §6 里 8.7 MB/序列/rank 就是按 fp32 算的。

好在这对体积几乎没影响：MoE 占全模型约 95%（288 experts × 3 × 4096 × 2048 × 42 层 ≈ 304 B 参数），34 层 KDA 投影合计才约 4.7 B（BF16 ≈ 9.4 GB），indexer / mHC / ViT 更是零头。W8A8 之后仍是 ~320 GB 量级，前面的估算不用改。对昇腾反而是简化：这 34 层走普通 BF16 matmul，不需要任何 modelslim scheme。

FP8 → INT8：可以，而且这是推荐路径

完全可以照搬 GLM-5.2 在昇腾的做法，步骤如下：

  • ① 取 BF16 权重 — 直接下 zai-org/GLM-5.3-Flash-BF16，或从 FP8 反量化（约 642 GB）；
  • ② 清洗 config.json — 删掉 quantization_config（quant_method: fp8 / weight_block_size），否则昇腾侧加载即报错；
  • ③ msModelSlim 量化 — dense/MLA linear 走 W8A8，MoE 走 W8A8_DYNAMIC；产出 quant_model_description.json，SGLang 自动识别（--quantization modelslim 只是显式覆盖开关）；
  • ④ ignore list（GLM-5.3 特有） — 直接照搬官方 modules_to_not_convert，明细见上表：34 个 KDA 层的全部权重、indexer 全套、mHC 全部参数、整个 ViT、所有 norm；
  • ⑤ 校准 — 288 专家 + top-8 路由，校准集要覆盖到足够多的专家才不会有冷专家掉点。DeepSeek 同量级 BF16→INT8 官方参考耗时 7–8 小时/轮，按多轮预留。

与 GLM-5.2 的差别只在第 ④ ⑤ 步：5.2 是纯 MLA + MoE，ignore list 简单；5.3 多了 KDA 整层 / mHC / ViT 三类必须排除的模块，专家数也从 DSv3 量级涨到 288。W8A8 的典型损失在 1% 以内，属于可接受区间。

W4A8 作为二期是现实的：GLM-5.1 的 w4a8 配方在昇腾已经量产验证，GLM-5.3 对应体积约 180 GB，A2 单节点 TP8 就能放下。但 mHC 对量化噪声敏感，W4 档要先单独验证精度，不要直接照抄 5.1 的 ignore list。

§7风险登记

中

参考实现仍在未合并分支上xinyuan/glm-5.3-flash-support 已公开且完整，但未进 main / 任何 tag，接口还会动，需要持续 rebase 跟踪。分支内 GLM-5.3 新代码对 npu|ascend 命中数为 0，后端层完全需要自建。

中

kpool 的分组 topk 没有昇腾对等物压缩那一半有 DSv4 的 torch.ops.npu.compressor 可照抄，打分有 quant_lightning_indexer，topk 之后的稀疏 MLA 完全不变。缺的是分组 topk：GPU 走 CUDA JIT fast_kpool_topk_transform_fused / fast_topk_v2，且代码对非 CUDA / 非 fp32 logits 直接 raise NotImplementedError。M0 先解硬拦、用 torch.topk 打通，再决定要不要写算子。

中

mHC 的 Sinkhorn 在 decode 吃算力算子可用性已不是问题（见 §1），但 20 次 Sinkhorn 迭代在小 batch decode 是 compute-bound —— llama.cpp 移植 DSv4 的实测里，量化更狠反而更慢（Q8_0 16.62 tok/s vs Q4_K_M 9.95 tok/s），说明这条路径不是权重带宽 bound。加上 4 路残差流让访存约 10×，可能吃掉 KDA 省下的收益。建议 M1 就在 A3 上对 DeepSeek-V4-Flash 做一次 decode profiling 拿基线。

高

FP8 权重无直读路径 + mHC 量化敏感A2/A3 无原生 FP8 matmul；softfp8_w8a16_matmul 已有算子但 SGLang 侧零引用，接入计划不在当前 NPU roadmap 的 10 项内。必须走 BF16 → msModelSlim W8A8（7–8 h/轮，多轮迭代），且 mHC 全部参数须留 fp32，否则 Sinkhorn 后噪声放大。

中

indexer 32 heads 在 TP16 下的切分现有 DSA backend 的 pad 逻辑是为「64 heads / TP8 → pad 到 16」写的；32/16=2 需要新的复制或 pad 策略，且 index_kpool 压缩在 A2/A3 无对应 epilog。

中

NPU Graph 兼容性官方特性矩阵里 NPU Graph 与几乎所有特性都只是「部分兼容」，仅 PrefixCache 为全兼容。新增 mHC buffer 与 KDA state indices 会加剧；还有 graph 数量上限（版本不匹配时需降到 ≤10）。

中

1M 上下文KDA 层的 recurrent state 天然串行，CP 语义受限；昇腾 roadmap 上 128K/256K CP 本身尚未完成。建议一期明确只承诺 128K。

低-中

A2 成熟度智谱官方 example/ascend.md 称 Atlas 800 A2 系列 “mostly untested”，与 SGLang 支持矩阵的 A2 全 ✅ 口径不一致。A2 形态建议排在 A3 之后。

低

视频路径依赖 torchcodec昇腾镜像内的可用性未验证；不通则视频输入降级为不支持，图片路径不受影响。
