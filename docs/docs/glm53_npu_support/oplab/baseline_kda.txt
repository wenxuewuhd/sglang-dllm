=== sweep: does anything in a KDA layer depend on sequence length? ===
  KDA is recurrent.  Its decode state is a fixed [64,128,128] fp32
  matrix per slot plus a [3,24576] conv window; the sequence length
  enters no shape, no stride and no loop bound.  First we prove that,
  then we measure all four lengths anyway.

  n=    1024: 12 tensors  (reference fingerprint)
  n=    4096: IDENTICAL to n=1024
  n=   32768: IDENTICAL to n=1024
  n=  131072: IDENTICAL to n=1024

  So any spread below is this machine's noise floor, not an n effect.
  (An honest O(1) claim has to be structural.  Measuring four identical
   workloads and finding them equal proves nothing on its own.)

     seq len   us/layer   x34 (ms)  vs shortest
      n=1024     293.29      9.972        +0.0%
      n=4096     293.45      9.977        +0.1%
     n=32768     297.94     10.130        +1.6%
    n=131072     300.02     10.201        +2.3%

=== slots: the knob that does move KDA is concurrency, not length ===
  4.19 MiB of fp32 ssm state per slot per layer.  The served TP1 recipe
  runs 16 slots = 2.34 GB across 34 layers, and it competes for L2.
  Slot 0 is always the one read, so only the pool size varies: this
  measures cache pressure, not a different amount of work.

  Read this as: a GEMM at ~1.0x the COLD floor of its own weight is
  finished.  There is no kernel work left to win there -- only fewer bytes
  (a smaller dtype) or fewer calls would move it, and both are model
  changes.  Compare the warm and cold rows before believing any ratio
  below 1.0: L2 here is ~168 MiB and it will happily hold a whole
  weight if you keep asking for the same one.
